Что есть: формат сейва со всем, что нужно «Продолжить» (персонаж, инвентарь/экипировка, души/эстус/пятно, последний костёр и зона, флаги событий по зонам, настройки); запись на карту памяти через `sceUtilitySavedata` (иконка, «Ash: DS1» в XMB) с двумя копиями A/B; запасной путь — файл с записью через временный + переименование; CRC-32 и проверки полей; асинхронная запись (кадры идут); тест-EBOOT с перезапуском эмулятора; демо «Продолжить» через настоящее меню `src/menu`.

**Не встроено в игру** (`src/game` — чужая зона): ниже готовый рецепт для интегратора. Игра пока пишет старый `ash.sav` через `src/progress/save.h`.

## Где лежит и почему так

- **Основной путь — `sceUtilitySavedata` в режимах без диалога (AUTOSAVE / AUTOLOAD)** **[придумал]**: `ms0:/PSP/SAVEDATA/ASHDS0001A/` и `…/ASHDS0001B/`, в каждой `DATA.BIN` (наш контейнер, зашифрован утилитой), `PARAM.SFO`, `ICON0.PNG`. В XMB видно «Ash: DS1», имя персонажа, деталь «зона / уровень / души / время». Проверено в PPSSPP [проверено, PARAM.SFO прочитан скриптом]:
  ```
  TITLE Ash: DS1        SAVEDATA_TITLE Пепел        SAVEDATA_DIRECTORY ASHDS0001B
  SAVEDATA_DETAIL Северное Прибежище Нежити / Уровень 5   Души 2234 / Время в игре 1:02   (копия B, №2)
  ```
- **Почему две копии:** у утилиты нет «переименовать», запись не атомарна. Пишем по очереди в ту копию, где **не** лежит самая свежая целая (сначала битая/отсутствующая, иначе более старая). Обрыв питания или выдернутая карта портит только записываемую копию, загрузка берёт целую с наибольшим `seq`. Это аналог «временный файл + переименование» **[придумал]**. Цена — две записи в XMB вместо одной.
- **Ключ шифрования обязателен.** Первый прогон без ключа: запись вернула `0x80110388` (`SCE_UTILITY_SAVEDATA_ERROR_SAVE_PARAM`) — эмулятор (`SavedataParam.cpp`, `MissingRequiredKey`, с комментарием «Hardware returns SAVE_PARAM for a save without one») требует ключ для `secureVersion 0` при 1536-байтной структуре [проверено в эмуляторе; на железе — **[версия]**]. Ключ — наша константа `SV_KEY` (16 байт); **менять нельзя никогда**, иначе старые сейвы не прочитаются.
- **Запасной путь — файл** `ash.sav` рядом с EBOOT (`ms0:/PSP/GAME/ASH/ash.sav`): пишется в `ash.sav.tmp`, старый удаляется, временный переименовывается (на fatms переименование не заменяет существующий файл). Обрыв между удалением и переименованием оставляет целый `ash.sav.tmp` — загрузка его подхватывает. Нет переименования — запись на месте (ловит CRC). Включается сам, если `sceUtilitySavedataInitStart` отказал или запись утилитой вернула ошибку; при загрузке читается всегда (берётся самый свежий из всех трёх источников). Новая игра со старым форматом `src/progress` в `ash.sav` его **не** прочитает (нет частей META/CHR1 → «нет сейва»).

## Формат (версия 1)

Контейнер `src/progress/save.h`: `"ASHS"`, версия 1, число частей, {тег, размер}, данные (выравнивание 4), **CRC-32 по всему**. Внутри части (все поля явно little-endian, без дампа структур — раскладка не зависит от компилятора):

| часть | содержимое |
|---|---|
| `META` | формат (1), `seq` (счётчик записей — побеждает больший), время в игре (с), зона (area, block: 18,1 = Прибежище; 10,2 = Храм Огня), **последний костёр** (id сущности события = `Ev.respawn`), флаги игры, время записи (тики RTC) |
| `CHR1` | имя (UTF-8, 64 байта = `MenuChar.name`), класс (`CharaInitParam` 3000…3009), пол, дар, причёска, уровень, 8 атрибутов (порядок `MA_*` меню), **человечность, души**, HP/макс, эстус/макс, смерти, `Progress.flags` |
| `STN1` | **пятно душ**: есть ли, зона, позиция (м, пространство PSP), души |
| `INV1` | **инвентарь**: до 64 записей {категория (оружие/броня/кольцо/расходники), заточка +N, количество, id строки EquipParam}; **экипировка**: 19 слотов (порядок `MSLOT_*` меню) — индекс в списке или −1 |
| `SET1` | настройки меню: схема А/Б, яркость, скорость камеры, инверсия X/Y, оверлей |
| `ZEVT` | **флаги событий по зонам**: до 4 зон × {area, block, блоб `ev_save_write` ≤ 8 КБ} |
| `ITMS` | **инвентарь `src/items`** как есть: блоб `itm_save_write` (записи, экипировка, активные руки, быстрый слот; ≤ 1 КБ, на 15.10 — 576 Б); пишется, только если `itm_size > 0` |

Незнакомые части при чтении пропускаются; формат новее нашего — отказ (`-5`), а не кривое чтение. Проверки при чтении: CRC, длины, души/эстус/пятно ≥ 0, уровень ≥ 1, конечные float, индексы экипировки в пределах списка. Любая ошибка — копия считается битой, в цель ничего не пишется.

Размер: пример с 2 зонами событий (1500 + 37 Б) и блобом инвентаря 576 Б — **2 480 Б** [проверено, нативный тест]; `DATA.BIN` на «карте» эмулятора 2 496–2 500 Б (шифрование +16) [проверено]. Память: `ash_save` — **≈175 КБ BSS** (`psp-size` по `libash_save.a`: 178 976 Б) [проверено] — буферы рассчитаны на худший случай 4 зоны × 8 КБ событий; если реальные блобы `ev_save_write` меньше, `SG_EVT_BYTES`/`SG_MAX_ZONES` можно уменьшить [оценка].

**Инвентарь.** Пока шла эта работа, в дереве появился `src/items` (другая задача, на 15.10 не закоммичен) со своим блобом `itm_save_write` / `itm_save_read` — он и хранится в части `ITMS` как есть (как блобы событий: формат держит владелец модуля). Интегратору: `s->itm_size = itm_save_write(&inv, s->itm_blob, SG_ITM_BYTES)`; при «Продолжить» — `itm_save_read(&inv, &db, s->itm_blob, s->itm_size)`. Часть `INV1` (список {категория, id EquipParam, заточка, количество} + 19 слотов) — форма без базы предметов (тесты, инструменты); при наличии `ITMS` игра её не читает, можно оставлять пустой. Пока меню показывает снаряжение и предметы из таблицы класса (`menu_fill_view_from_char`), поэтому после «Продолжить» экраны снаряжения/инвентаря — стартовые для класса.

## API

```c
#include "savestore.h"     /* + savegame.h, save_menu.h */
SaveStore store; static SaveGame sg;
sv_init(&store, SV_BACKEND_ALL, 0);                 /* утилита A/B + файл "ash.sav" */
int has = sv_read_sync(&store, &sg) == SV_OK;       /* при запуске, до титула: ~30 кадров в эмуляторе */
menu_set_has_save(&menu, has);

/* запись без остановки игры: */
sv_write_begin(&store, &sg);                        /* копирует sg сразу, seq = новейший + 1 */
... каждый кадр: int r = sv_poll(&store);           /* SV_BUSY ... затем SV_OK / SV_ERR один раз */
/* или синхронно: sv_write_sync(&store, &sg) */
```
`sv_busy()` — идёт ли операция; вторая операция во время первой отвергается (`SV_ERR`) — копите «грязный» флаг и пишите после. `store.last_src` / `src_result[]` / `src_seq[]` — откуда прочитали и что с каждой копией (для лога). Мосты: `sg_from_progress` / `sg_to_progress` (души, эстус, смерти, HP, пятно, флаги; при смерти сохраняется то, что даст перезагрузка — правило живёт в `prg_save_write`), `sg_from_menu_char` / `sg_to_menu_char`, `sg_from_settings` / `sg_to_settings`, `sg_to_view`, `sg_zone_put` / `sg_zone_get`.

## Рецепт для интегратора (`src/game/asy_game.c`, `asy_main.c`)

1. CMake: `ash_asylum` линкует `ash_save` (он тянет `ash_progress`, `psputility`, `psprtc`).
2. Состояние в `Game`: `SaveStore store; SaveGame sg; int save_dirty; float play_s;` + `stain_area/stain_block` (зона, где умер — ставить в обработчике смерти игрока).
3. Сбор сейва (вместо тела `game_save`):
   ```c
   static void game_save(Game *g, const char *why) {
       if (sv_busy(&g->store)) { g->save_dirty = 1; return; }      /* дописать после текущей */
       SaveGame *s = &g->sg;                       /* персонаж/настройки уже лежат там с MEV_NEW_GAME/CONTINUE */
       sg_from_progress(s, &g->prg);
       s->stain_area = g->stain_area; s->stain_block = g->stain_block;
       s->area = g->zone_area; s->block = g->zone_block; s->bonfire = g->ev.respawn; s->play_s = (u32)g->play_s;
       SgZoneEvents *z = sg_zone_put(s, s->area, s->block);
       if (z) z->size = ev_save_write(&g->ev, z->data, SG_EVT_BYTES);
       s->itm_size = itm_save_write(&g->inv, s->itm_blob, SG_ITM_BYTES);   /* src/items */
       sv_write_begin(&g->store, s);
       asy_log(g, "save (%s) begin", why);
   }
   /* в шаге кадра: */
   int r = sv_poll(&g->store);
   if (r == SV_OK || r == SV_ERR) asy_log(g, "save %s -> %s seq %u", r == SV_OK ? "ok" : "ERR",
                                           sv_src_name(g->store.last_src), (unsigned)g->sg.seq);
   if (r != SV_BUSY && g->save_dirty) { g->save_dirty = 0; game_save(g, "dirty"); }
   ```
   Поводы уже есть: `EV_CMD_SAVE` (отдых у костра), `PRG_REQ_SAVE` (автосейв `src/progress`, не чаще раза в 10 с). Добавить: **при смене зоны** — перед выгрузкой старой зоны (её флаги событий уходят в `ZEVT`, новая зона пишется после загрузки с `s->area/block` новой), и `MEV_TO_TITLE` (меню) — `sv_write_sync`, чтобы выход в титул не потерял сейв.
4. Запуск: `sv_init` → `sv_read_sync` → `menu_set_has_save(has)` → титул.
5. `MEV_NEW_GAME`: `sg_init(&sg); sg_from_menu_char(&sg, &m.chr); sg_from_settings(&sg, &m.set);` → новая игра (сейв появится у первого костра).
6. `MEV_CONTINUE` (сейв уже прочитан при запуске): `sg_to_menu_char(&sg, &m.chr); sg_to_settings(&sg, &m.set);` → загрузить зону `sg.area/sg.block` → `ev_save_read(&ev, sg_zone_get(...)->data, size)` → `sg_to_progress(&sg, &prg)` → `itm_save_read(&inv, &db, sg.itm_blob, sg.itm_size)` → поставить игрока на `ev_respawn` (костёр `sg.bonfire`) → `menu_fill_view_from_char` + `sg_to_view` для экранов меню.
7. Старый путь `save_write_file(SAVE_PATH, …)` / `save_read_file` в `asy_game.c` убрать; автопилот (`scenario != ASY_SC_NONE`) по-прежнему стартует без сейва.

## Не проверено / не сделано

- **Железо.** Утилита, шифрование с ключом, A/B, время записи на настоящей карте Memory Stick — только эмулятор. Порча копии проверена порчей зашифрованного файла на «карте» эмулятора (PPSSPP расшифровал, поймал наш CRC); на железе утилита может сама отказать в загрузке битой копии — для нас это то же «копия негодна» (`-100`), путь тот же [версия].
- Обрыв питания посреди записи не моделировался (только порча готового файла и «удалили — не переименовали» в нативном тесте).
- Встраивание в `src/game` (рецепт выше), автосейв при смене зоны — за интегратором; `src/items` в сейв попадёт только после встраивания (часть `ITMS` проверена на синтетическом блобе, не на настоящем `itm_save_write`).
- Очистка/удаление сейва из игры не сделаны (в XMB удаляется штатно).
